## Context

现有会话由 Better Auth 和官方 Drizzle adapter 管理，B06 品牌恢复读取权威会话中的邮箱标志。Better Auth 的默认邮箱验证链接可重复提交，需要应用为用户可见的链接附加原子消费；密码重设沿用 SDK 的存储、消费、哈希和撤销。

## Goals / Non-Goals

- 实现经浏览器和真实应用 HTTP 核对的两条邮件流程，复用现有账户页、消息目录和品牌恢复。
- 真实供应商采购、配置与可达性、试点开放和实际付费属于后续任务。

## Decisions

- 使用独立同源 POST 入口和严格 Zod 合同。Better Auth 底层邮件端点只允许服务端调用。落地页通过片段携带令牌，由用户显式提交，禁止公共缓存和 Referrer，完成时从地址删除令牌。
- 邮箱验证使用存于 Better Auth 验证表的随机令牌，数据库对标识做哈希。经账号绑定检查后，通过同一事务消费令牌并调用 SDK 验证。密码重设使用 Better Auth 自带小时链接、密码哈希与会话撤销。SQLite3 使用即时事务，PostgreSQL 使用专属事务连接及账号行锁。密码登录创建会话和密码重设共用该事务边界，旧密码登录在重设提交前创建的会话也会被撤销。
- 一张限流表按动作与账号/IP 的 HMAC 作为主键，两条桶记录以固定顺序锁定。每条记录最多保存该流程限额数的时间戳，过期索引用于有界清理；单次请求的查询数固定，与用户量无关。通过双方言迁移、全量 DDL 和查询计划核对部署。
- 配置可信网关覆盖来源地址头，缺失或无效时停发。POST 限额通过后用 Next.js 响应后任务处理账号查找与投递，保持外部响应一致。可配置 HTTPS JSON 邮件网关，隔离接收器在回环测试。故障只记录流程与随机追踪标识。

## Risks / Trade-offs

响应后投递属于尽力执行。若进程在接受请求后停止，用户可能需要在限额内重发。正式入口开放前须经 #21 核验实际投递、网关边界和日志配置。
