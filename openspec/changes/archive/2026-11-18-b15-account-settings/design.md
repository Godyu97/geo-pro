# Design

## Context

工作台布局以请求级会话提供称呼，Better Auth 已用官方 Drizzle 适配器承接两种数据库。已实现的界面语言选择通过服务端 Cookie 保存，设置页可以直接使用。详见 [提案](proposal.md)。

## Goals / Non-Goals

- 用现有账号和会话提供资料页，支持 Unicode 称呼、服务端确认保存和安全导航恢复。
- 将资料写入保持在 Better Auth 的现有边界内，沿用单账号更新和两种后端。语言偏好仍由现有界面 Cookie 承接。
- 安全入口接续当前会话的退出操作，数据管理入口展示实际可用性。密码找回、邮箱验证、导出、删除与品牌业务各自按对应 Issue 推进。

## Decisions

1. 采用 `/dashboard/settings` 对应 PAGE-08，加入工作台导航和 B02 的精确返回白名单。路由导出账户 feature 的服务端页面，页面独立校验会话，只把显示和提交所需的字段传给局部表单。该页将工作台已有的语言选择和退出按钮放入对应设置区。
2. 在 Better Auth 的 `/update-user` 处理链上应用严格 Zod 请求合同，称呼规则与注册共用。Better Auth 的会话和来源校验、现有写入和会话更新继续生效。设置表单随请求提供所见账号的标识，服务端只用它检测过时页面。当前会话仍是唯一写入目标。
3. 成功响应后采用服务端路由刷新，同步工作台称呼。保留失败或切换语言时的页内输入，保存结果使用本地化消息。失效会话返回登录位置，用户重新登录后才可再次主动提交。
4. 写入复用认证用户主键上的一次单行更新，原子性沿用数据库适配，独立重试或并发更新仅作用于该会话的账号。数据合同中没有新增表、索引、缓存、迁移或依赖。

## Risks / Trade-offs

- 直接调用旧更新入口并提交额外字段会收到校验错误。验证包覆盖当前账号及另一账号的持久状态，确保错误调用不会部分修改。
- 会话或数据库可能在提交期间变化。设置页在收到明确成功前保持草稿，旧身份冲突要求刷新，无法确认的结果只给检查或主动重试入口。

## Migration Plan

代码随现有 Next.js 构建发布，使用当前迁移和账号行。不需转换已有称呼或会话数据。
