# Design

## Context

B04 已提供品牌归属、实体版本和回环合成资料入口。B06 与 B07 使用同一个负责人事务锁处理冻结、恢复与清除。

## Goals / Non-Goals

在品牌详情中提供可继续编辑的事实和原文，并建立内容模块可在服务端使用的版本资格合同。内容工作流和真实资料启用由后续 Issue 承接。

## Decisions

- `brand_fact_paste` 用来保留独立原文修订，`brand_fact_version` 记录按事实分组、依实体版本绑定的候选和审批。来源字段与主张同版保存，因为只有在该版使用它们。依赖登记表以事实和内容精确版本为键，可从任一方向批量查询。待审、待交付、已经在线和历史引用的影响由当前事实状态推导。
- 复用同一参数化 DAO 和负责人写锁。PostgreSQL 锁定负责人行，SQLite 使用现有 `BEGIN IMMEDIATE`。版本编辑对比修订号，新增以客户端 UUID 幂等登记。品牌删除级联，冻结期间禁止读写。
- 每次粘贴可按行离线预览或手工拆卡，候选保留可定位的原文和片段。原文及来源始终私有。公开投影只包括事实标识、版本与用户明确许可的主张。
- 使用日历有效日期，选择的日期在 UTC 结束时失效。价格和长期事实的复核时间计算独立。冲突由同一事实系列中有效的批准版本与新主张比较，确认新版时可显式撤销冲突版本。
- 分页使用品牌下的创建时间及 ID 索引；事实历史查询使用品牌、事实和版本唯一键；双向依赖按品牌和版本索引。公开资格以固定上限批量读取。无外部服务、缓存和额外依赖。

## Risks / Trade-offs

- 下游正式内容尚未接入。通过显式测试依赖验证资格和影响，接入真实消费者时重跑。
- 与撤销竞争的正式交付须在同一事务持有负责人锁并重新核验。已经导出的包无法召回。

## Migration Plan

生成并审查 SQLite3 和 PostgreSQL 增量迁移与全量 DDL。验证双方言空库导入和已有 B04 数据升级。部署沿用现有迁移流程，应用回滚时保留新增表中的版本与原文。
