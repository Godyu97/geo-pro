## DAO 边界与双数据库兼容

- **调用链**：薄页面/API → `src/features/<domain>/` 服务或用例 → DAO → 数据库适配。业务查询收敛到 DAO；领域查询按需留在对应 feature 的服务端目录，连接与方言适配放在 `src/lib/db/`。保持模块化单体，不新建独立服务或通用 CRUD 框架。
- **合同与隔离**：DAO 接收已校验的输入和服务端确认的资源范围，返回业务所需数据，不向上层泄漏驱动对象或方言。查询与写入必须带适用的用户/品牌归属条件，不能只按外部传入的 ID 操作；DAO 不取代入口会话校验。
- **显式连接目标**由服务端配置确定。默认后端类型为 PostgreSQL，连接地址必须填写。使用 SQLite 时显式指定已迁移的文件。连接失败应返回可解释错误，保留现有连接目标与数据。
- **方言隔离**：SQLite 与 PostgreSQL 分别维护适用的 Schema 和迁移，不能共用 PostgreSQL SQL 文件冒充兼容。类型、时间、金额、布尔/unknown、JSON、排序、唯一约束、外键、批量参数及冲突写入的差异在适配边界处理；对外保留同一 ID、版本和错误语义。验证 SQLite 连接实际启用外键约束。
- **事务与并发**：由业务用例明确事务边界，DAO 操作共享该事务上下文；需要原子完成的版本检查、幂等登记与业务写入不能拆成互不关联的提交。分别处理并验证锁竞争、唯一冲突和回滚；未知写入结果先核对，不盲目重试。
- **认证边界**：Better Auth 继续使用官方 Drizzle Adapter，认证 Schema 走官方生成链。SQLite 支持必须同步核对 Auth provider、Schema 生成、迁移和会话撤销链路；不手改生成表或用业务 DAO 替代框架内部认证逻辑。

接口围绕已授权的真实用例定义；支持两种后端不意味着每个实体都需要一套仓储类、工厂或提前铺设空目录。

## cache 合同与失败行为

- **同一入口**集中在 `src/lib/cache/`。常规应用要求显式 `REDIS_URL`；隔离测试可直接选择 memory。连接配置和客户端实例保持 `server-only`，凭据留在服务端。
- **最小一致语义**：按实际用例提供读取、写入、删除与必要的批量操作；明确 miss、缓存空值、序列化、TTL 单位与过期行为。缓存条目有过期边界，两个后端遵守相同合同。
- **memory 边界**为单进程、重启清空。隔离验证应覆盖容量与 TTL；Redis 跨实例读与写后失效单独验证。
- **权限与版本**：按适用的用户/品牌、对象版本和查询条件构造 key，指标缓存还要包含完整统计 scope 与规则版本。原始业务与指标缓存保持业务 scope，不按界面语言重复复制原始证据；任何缓存的本地化 HTML、Metadata、接口展示消息或渲染报告则必须包含有效 `locale`（与 [Web 多语言规范](i18n.md) 一致），防止英文与中文响应串缓存。先鉴权再访问缓存；撤销权限或删除数据后，旧缓存不能继续放行访问。缓存不承载唯一的证据、预算、幂等或审批状态。若后续在数据库中持久化用户界面语言偏好，字段与查询路径须同时兼容 SQLite3 与 PostgreSQL。
- **写后失效**：数据库提交成功后失效受影响缓存或切换版本键，避免在事务提交前写入成功结果。失效失败须记录并安排重试或绕过对应缓存，限制旧值可见窗口；不把已提交的业务写入伪装为未发生。事实/内容修订、分析版本变化与删除都要覆盖关联缓存。
- **Redis 不可用**：普通可重建读缓存可在受控负载下回源数据库并记录故障；不能静默切到 memory 并假装共享缓存正常。依赖共享原子状态的能力不能按普通缓存降级；若未来有此需求，需单独定义一致性与失败行为。

Redis 的缓存用途已确认；这不等于授权引入 Redis 队列、分布式锁、后台 Worker 或调度平台。缓存命中也不能替代 SQL 与索引优化。

## SQL 性能与批量操作

1. **先整理查询链**：识别输入依赖，避免逐行 `await` 查询形成 N+1。列表关联优先使用合适的 JOIN、集合查询、`IN` 批量读取与分组聚合，再在内存中映射结果；不要为每条记录再查一次详情或统计。
2. **控制并发**：独立且无法合并的查询才考虑有界并发，结合连接池、SQLite 写入竞争与事务要求限制数量。用无上限 `Promise.all` 替换循环不算批量 SQL 优化；有真实依赖或事务顺序要求的操作可以串行并说明原因。
3. **控制数据规模**：仅取必要字段，列表必须有分页上限及稳定排序；大结果集按需采用游标分页。不加载全表后在应用中筛选、分页或计算数据库可完成的聚合。
4. **批量写入有边界**：按后端参数与语句大小限制分块插入、更新或 upsert，明确冲突键、事务边界与部分失败结果。重试不重复成功项，不跨越产品的版本、幂等和预算约束。
5. **参数化与计划检查**：查询值使用参数绑定，动态排序/字段采用白名单。按实际过滤、连接与排序检查索引及 `EXPLAIN` / SQLite `EXPLAIN QUERY PLAN`；不能只凭 SQL 条数少或存在索引就判定高效。
6. **保留可核验证据**：在开发或隔离库记录代表性数据量、SQL 次数、查询计划与耗时，并比较列表规模变化后的查询次数。合成性能数据明确标为测试，不写成真实监测或客户效果；不编造统一延迟门槛或优化比例。

## 最小表结构与索引审查

- [公共 SPEC](../04-产品功能规格-SPEC.md) 的对象是业务语义，**不要求一个对象对应一张表**。按当前任务的数据生命周期、事务和查询需求决定存储形式，不一次性建立 M0–M2 全部表，也不为每个状态、标签或页面创建表。
- 每张新增表说明用途、为何现有结构不能承接、主要读写路径、归属/版本和保留删除行为。精简表数量不能丢失原文不可变、独立状态、版本追溯、幂等或权限隔离；认证表遵循生成合同，不为减少数量擅自合并。
- 常用于过滤、连接、排序或约束的字段应可被有效查询与索引；低频扩展信息或不可变快照可按需使用结构化 JSON，但不能把所有关系塞入一个大字段而失去约束，也不为未发生的分析提前建大量汇总表。
- 为主键、必要唯一规则、常用关联与实际访问路径审查索引。复合索引的列顺序根据过滤与排序确定；避免重复、无用途或低收益索引，并评估写入成本。小表合理扫描不等于缺陷，不要求每列建索引。
- 表和索引变更分别生成并审核适用后端的迁移，再应用到明确的开发目标库；验证升级路径、约束与查询计划。禁止用 `push` 替代迁移，不通过删除既有证据或重建数据表掩盖兼容问题。
- 全量 DDL 必须覆盖该后端全部应用表、约束与索引，在每次 Schema/migration 变更中同步生成和检查；不能只维护增量 SQL 或手改快照。具体命令与快速部署边界见 [数据库部署说明](database-deployment.md)。
